## Product behavior

The device-local **Motion smoothing** setting has three requests:

| Request | Effective behavior |
| --- | --- |
| **Off** | Preserve the player's configured cadence and output. |
| **MPV** | Use MPV display-synchronized temporal resampling where the active MPV output supports it. |
| **Neural** | Use the connected native or model-backed interpolator on the active decode/presentation path. Apple uses VideoToolbox for supported streams; eligible Android MPV paths try ANVIL-S/M with QNN HTP, then LiteRT NPU/GPU packs; Windows/Linux attach the PME model filter when the verified model pack is installed. Windows uses its bundled Windows ML runtime and catalog providers; Linux uses its selected ORT runtime/providers. Unsupported content falls back to MPV smoothing where available. |

Neural presets are **Performance**, **Balanced**, and **Quality**. On macOS and iOS device builds, Apple's cadence-aware `VTFrameRateConversion` path uses mpv's display-slot schedule to choose intermediate timestamps, capped by preset budgets of one, three, or seven generated frames. When display-slot data is unavailable or the low-latency fallback is active, presets use uniform 1/3/7-frame grids. This follows the active display cadence instead of forcing a fixed 2×/4×/8× multiplier. Desktop Performance uses bundled 540p ANVIL-S, Balanced uses upstream 1080p ANVIL-S, and Quality uses upstream 1080p ANVIL-M; Android Performance/Balanced use ANVIL-S and Quality uses ANVIL-M; Android selects burst power for Performance and sustained power for Balanced/Quality. The desktop PME filter passes the selected preset to ONNX Runtime's QNN provider as `burst`, `balanced`, or `sustained_high_performance`; Windows resolves QNN through the Windows ML provider catalog. That HTP setting applies only when QNN actually owns the session; OpenVINO, CUDA, DirectML, Vitis AI, and CPU runs report it as not applicable. The MPV fallback does not consume the Neural preset. Diagnostics report the HTP mode only after the QNN runtime accepts it. VideoToolbox does not expose reliable per-frame ANE/GPU placement through this API.

**Only when plugged in** is an opt-in Neural power guard, enabled by default. It checks the platform battery state before provider setup and listens for a switch to battery during playback. When the platform confirms battery operation, Apple interpolation is disabled and model-backed MPV filters are removed; MPV smoothing remains active where available. It resumes Neural on the next item after external power returns rather than hot-starting a provider mid-stream. Unknown or unsupported power status remains eligible so a battery-less desktop or TV is not treated as unplugged.

Motion processing is independent of **Match Content Frame Rate** and **Match Refresh Rate**. Those choose display cadence; this engine processes or synthesizes video frames for that cadence.

## Implemented in PlezyNG

`MotionProcessingService` applies `video-sync=display-resample`, Mitchell temporal scaling, and interpolation before each MPV `loadfile`, including reused-player episode transitions. It saves and restores the user's original MPV timing properties. Windows/Linux/Android MPV smoothing is limited to progressive SDR VOD up to 1080p at 24/30 fps; Android Neural's midpoint frames also use MPV's display-sync scheduler. At playback startup it prepares the known Windows/Linux MPV paths; diagnostics resolve the request against the active `current-vo` and actual interpolation state.

- **Windows:** the embedded MPV output is `gpu-next`.
- **Linux Wayland:** embedded `vo=libmpv` receives the active monitor rate through `display-fps-override`. After a successful EGL swap, the runner calls `mpv_render_context_report_swap` so libmpv receives presentation timing.
- **Android MPV:** an explicit MPV request asks the native video-output arbiter to move eligible progressive SDR video up to 1080p at 24/30 fps from direct MediaCodec presentation to its GPU renderer. The arbiter owns surface handoff and keeps the configured decoder choice; Off removes only the motion request, allowing any other GPU requirements to remain active. Neural first tries ANVIL/QNN on a supported Snapdragon path, then LiteRT CompiledModel on an available NPU, then LiteRT GPU. LiteRT rejects CPU-partitioned sessions; when setup fails, the service configures MPV smoothing. ANVIL's `gpu-next` route uses software decoding with exported motion vectors. Live, transcoded, HDR/Dolby Vision, interlaced, and out-of-scope cadence/resolution remain on the configured output.
- **Apple AVFoundation:** the opt-in `avfoundation-motion-interpolation` option and `avfoundation-motion-preset` tier configure an MPV VideoToolbox bridge. macOS 15.4+ and iOS/iPadOS 26+ device builds prefer `VTFrameRateConversion` when the runtime reports it supported; mpv's `video-sync=display-resample` schedule supplies each source frame's display-slot count, and the processor accepts caller-selected phases. If that processor is unsupported or cannot start, the native bridge falls back to `VTLowLatencyFrameInterpolation` when supported. tvOS and compile targets without the general API use the low-latency path directly; it offers uniform 1/3/7-frame grids. Session creation stays off the render thread. It inserts generated frames before the current source sample and stays off for HDR/Dolby Vision, interlaced, non-24/30 fps, over-1080p, non-normal playback rate, OSD-composited, or geometry-rendered frames. It skips a pair when its recent processing time cannot fit the current presentation budget. The `video-out-interpolation` property reports `ready` or `active` only when the current stream passes those path/cadence guards; unsupported content, seeks, and presentation resets revoke eligibility until the path is valid again.
- The app arms Apple's Neural request before the file opens only when the selected version reports progressive SDR video at 24/30 fps within the initial 1080p scope and the active VO is AVFoundation. The native VideoToolbox path still checks actual frame format, HDR transfer, geometry/OSD state, and timing budget per pair. The eligibility decision is retained for the session so an in-player mode or preset change cannot bypass the open-time gate; a missing version, dimensions, selected video track, scan type, or cadence leaves Neural off.
- **Diagnostics:** the performance overlay reports actual video output, display rate, `video-sync`, interpolation state, source/render frame rates, and drops. Android ANVIL and desktop PME report cumulative generated-frame and decoded source-frame counts; the overlay shows the measured synthesis-to-source ratio. Android ANVIL also reports the QNN inference p95 over the latest 64 samples, deadline misses, scene-cut bypasses, and the power mode accepted by the HTP runtime. Desktop PME reports its selected HTP mode only when QNN is the active provider; non-QNN providers identify that field as not applicable. It resolves the requested mode against the active output, including ExoPlayer and unsupported MPV paths, and distinguishes a Neural request falling back to MPV from Neural inference.
- **Typed playback report:** `PlaybackCapabilityReport` groups the active output, decoder, pixel format, coded source dimensions, source FPS, HDR classification, Dolby Vision source profile, display/render rates, dropped frames, renderer state, neural-provider telemetry, and the cached platform thermal tier. The performance overlay shows an HDR yes/no row only when source transfer evidence supports that classification. HDR is true only for recognized PQ/HLG transfers, MPV HDR10 static metadata, or ExoPlayer HDR metadata; it is false only for recognized SDR transfers and unknown for ambiguous or unreported transfers. In particular, linear transfer is not assumed to mean SDR. Known HDR/Dolby Vision, over-1080p, or out-of-scope cadence resolves the effective mode to Off in diagnostics. Missing metadata stays unknown; it is not converted into a claim that the stream is SDR. Provider readiness is kept separate from observed generated output. The Android filter reports `qnn-htp-vN-ready` / `qnn-htp-vN` or `litert-npu-ready` / `litert-npu` and `litert-gpu-ready` / `litert-gpu`; the ready suffix appears before the first successful inference and the active name only after execution. It also reports generated-frame count, p95 inference latency, misses, and scene-cut bypasses. Windows/Linux read the matching `plezy-pme` filter metadata when available. ExoPlayer reports its active surface and decoder, while webOS is identified as its native player path without inferring access to the TV's MEMC controls. An installed or initializing provider is never displayed as generated-frame activity.
- **Thermal governor:** Android samples `PowerManager` status on API 29 and later before ANVIL setup and polls every five seconds while Neural is active. Moderate or higher pressure removes ANVIL and falls back to MPV smoothing when available. Apple reads `ProcessInfo.thermalState`; serious or critical pressure turns off VideoToolbox interpolation. If a provider transition fails, the report does not claim Neural paused and the governor keeps monitoring and retries. A new item checks the OS tier again before preparing Neural. Missing status fails open. The overlay shows the most recently reported tier.
- **Live playback:** live opens restore the saved MPV timing properties. The diagnostics resolver also receives the live/VOD state and reports motion processing as off for live playback, even when a global request is saved.
- **Settings:** Off, MPV, Neural, and the Performance/Balanced/Quality neural presets are selectable across players. Android Neural may switch an eligible H.264 stream to software decoding to expose motion vectors and CPU-readable frames. Android MPV can change only the video output for its eligible range and retains the decoder preference. Off restores the configured output. Unsupported streams continue normal playback and report the effective fallback.

## Runtime and model architecture

There is no single hardware provider that works on every platform. The engine needs one model/session contract with provider adapters and a platform-owned frame bridge:

1. **Common inference API:** PME is compiled against ONNX Runtime C API v27 or newer. Windows pins the stable Windows ML 2.4.89 package, which supplies ONNX Runtime 1.27.1 and the Windows ML C execution-provider catalog. The Linux AMD manifest selects the built-in MIGraphX provider; only that explicit marker permits PME to request C API v23 for AMD's ROCm 7.2.1 ORT 1.23.2 wheel. The pinned ANVIL-S model completed inference on the RX 7900 XT with CPU fallback disabled. AMD's newer ORT 1.29.0 / ROCm 10.1 plugin lists `gfx1100` Radeon GPUs as supported, but the pinned ANVIL-S graph currently executes entirely on CPU through that plugin, so it is not used for this model. Windows orders catalog-managed QNN NPU, OpenVINO NPU, Vitis AI NPU, QNN GPU, NvTensorRtRtx GPU, MIGraphX GPU, and OpenVINO GPU, then bundled DirectML GPU. Linux registers OpenVINO, AMD MIGraphX, and CUDA providers in manifest order. The standalone `onnxruntime-ep-openvino` Plugin EP is used where supplied; the deprecated in-tree OpenVINO EP is not packaged. Linux runtime lookup accepts `PLEZY_PME_RUNTIME_DIR` before checking the app bundle; it expects PME, ONNX Runtime, the provider manifest, and any listed provider plug-ins in that directory. For AMD multi-GPU systems, `ROCR_VISIBLE_DEVICES` can be set for the PlezyNG process to limit which devices the runtime sees; provider device IDs are relative to that visible set. DirectML uses ORT's provider API with sequential execution and memory-pattern allocation disabled. Catalog and plugin providers are accepted only when ONNX Runtime assigns the model output to the requested provider/device; CPU EP fallback is disabled for accelerator sessions. Apple uses its native VideoToolbox interpolation route.
2. **Apple native effects:** `vo_avfoundation` has a native `VTFrameProcessor` bridge. On supported macOS and iOS device builds, `VTFrameRateConversion` accepts arbitrary phases; the bridge uses mpv's `num_vsyncs` schedule to select display-slot timestamps and caps synthesis to the selected preset budget. If the general conversion processor is unsupported or fails to start, the bridge falls back to the low-latency API; tvOS and targets without the general API use that uniform interpolation grid directly. The provider initializes off the render thread, accepts the OS-reported CVPixelBuffer formats, inserts generated frames before each source sample, and exposes `video-out-interpolation` states. All paths accept progressive SDR 24/30 fps streams up to 1080p at normal playback rate, avoid OSD-composited and geometry-rendered frames, and bypass when the measured deadline budget is too small. Dolby Vision and HDR are excluded. Apple's VTFrameProcessor API debuted on macOS 15.4 and is available on iOS 26; each processor's runtime support, dimensions, and pixel formats are checked. The provider reports VideoToolbox; its API does not expose reliable per-frame ANE/GPU placement.
3. **ANVIL model and Android HTP path:** ANVIL-S/M is the selected MIT model family; RIFE remains a benchmark reference. ANVIL refines frames prealigned from H.264 decoder motion vectors, so the model file alone is not a frame interpolator. The Android filter is carried as `0142-android-anvil-qnn-filter.patch` plus `0144-android-anvil-litert-provider.patch` in the pinned mpv-build Android series. It preserves the QNN HTP context route and adds LiteRT CompiledModel over the same float NHWC ANVIL input/output contract. It requires software H.264 decode with motion-vector export and initializes the selected runtime asynchronously. A coarse YUV scene-cut gate passes suspicious transitions through and exposes its bypass count in filter metadata. QNN contexts are keyed by SoC, HTP architecture, and fixed shape; LiteRT model variants are separately pinned by shape, provider class, byte count, and SHA-256.
4. **Android LiteRT providers:** the Android app packages the LiteRT 2.3.0 C++ runtime, GPU accelerator, and Maven runtime AARs for Qualcomm, MediaTek, Google Tensor, and Intel OpenVINO after checksum verification. ANVIL's model pack uses static W8A8 quantization for JIT NPU and float32 for GPU; optional Samsung and Google Tensor AOT exports carry their exact target SoC in the model manifest. Android capability reporting intersects packaged provider libraries with the reported SoC family and ABI, rather than presenting every packaged plugin as usable on every device. Google Tensor selection requires a matching Tensor_G5 or Tensor_G6 AOT record; the generic JIT record is never selected there. The C ABI selects NPU first, rejects sessions with CPU execution, then tries the float GPU model. The filter reports only `litert-npu` or `litert-gpu` after that provider executes. The performance overlay names Qualcomm AI Engine Direct, MediaTek NeuroPilot, Intel OpenVINO, Samsung Exynos, or the exact Google Tensor generation from the selected NPU model record; a GPU fallback remains identified as `litert-gpu`. It uses aligned host buffers and currently copies into LiteRT tensors; AHardwareBuffer zero-copy is not claimed for this software-decoded motion-vector path. Android NNAPI is not used. LiteRT documents Exynos E9955/E9965 support. Samsung packaging accepts both LiteRT provider plugins and the matching LiteCore Android shared libraries through `PLEZY_LITERT_SAMSUNG_RUNTIME_ROOT`; the LiteCore libraries are staged as app assets, copied into app-private storage, and exposed to LiteRT through `EXYNOS_AI_LITECORE_ROOT`.
5. **GPU processing:** the ANVIL Android path uses Vulkan for prealignment and output composition. PME uses GPU compute for frame packing, flow upsampling, timestamp-specific warps, and fusion so the model provider can focus on flow refinement. GPU shader scaling already present in Plezy remains a separate spatial-enhancement path. RIFE/ncnn is a comparison tool, not the selected shipping model.
6. **NPU and GPU adapters:** ONNX Runtime supplies the shared desktop model API. Android uses QNN HTP and LiteRT CompiledModel. Windows obtains QNN, OpenVINO, Vitis AI, NvTensorRtRtx, and MIGraphX from the Windows ML catalog, with its bundled DirectML GPU provider as fallback; Linux loads configured OpenVINO, AMD MIGraphX, or NVIDIA CUDA providers. These labels come from the runtime's model-output provider/device report, not from a platform guess. webOS and Tizen retain native playback paths; app-controlled interpolation needs a controllable frame-processing interface from those TV platforms.
7. **MPV renderer fallback:** display-synchronized temporal interpolation is available on supported outputs. The Android service configures renderer interpolation before opening the stream so it remains active if ANVIL's asynchronous provider cannot open. The desktop PME filter bypasses model output after cuts, unsupported cadence, missing motion vectors, provider errors, or missed deadlines; MPV smoothing remains available where the renderer supports it.

The common native boundary is `libpme`, a stable C ABI used by the MPV `vf_plezy_pme` filter. The filter owns decoded-frame pairs, timestamps, generated frames, flushes, and bypass decisions. Provider libraries and model formats stay behind that ABI. Frame processing occurs before subtitle and OSD composition so text and graphics are not interpolated.

The first desktop adapter is intentionally narrow and currently emits a single midpoint frame (2×). It scales frames to the selected static model shape, runs CPU preprocessing or optional Vulkan preprocessing, invokes ONNX Runtime, reconstructs the model-resolution output, and upscales synthesized output to source dimensions. These stages run on a dedicated worker. The filter keeps the current pair pending while its callback returns, then wakes through mp_filter_wakeup() when the result is ready. Its source-pair deadline clock starts when the pair is submitted to the worker and includes dispatch delay, workspace allocation, preprocessing, inference, and reconstruction. If the midpoint misses that measured budget, the filter emits the original source frame. Only one pair can be in flight, so this removes inference from the callback but does not yet overlap the next pair or eliminate pair latency. If the worker cannot start or accept a pair, the filter passes the source frame through and keeps Neural off that pair. The pinned Linux app artifact still needs rebuilding to enable Vulkan. The local 7900 XT qualification build enabled Vulkan and selected Radeon RX 7900 XT for both PME and Vulkan; it processed the complete 540p model-resolution path. Windows can also select AMD Vitis AI for a supported Ryzen AI NPU or DirectML for a supported GPU when the corresponding provider-enabled ORT runtime is packaged and the model is accepted by that provider. The app selects software decoding for this route because hardware decoders do not consistently export FFmpeg motion-vector side data. The local 540p Performance path met the 1080p24 filter deadline in repeated playback; display presentation, visual quality, and other presets remain unqualified.

```text
MPV decoder → PME frame filter → video output
                  │
                  ├─ GPU resize / color packing
                  ├─ NPU or GPU flow inference (once per source-frame pair)
                  ├─ GPU flow warp and occlusion-aware fusion (per display timestamp)
                  └─ cut / confidence / deadline checks → synthesized frame or source passthrough
```

The engine should reuse one flow result for every output timestamp between a source-frame pair. A GPU performs flow upsampling, warping, and fusion; the NPU is used for operators it can execute efficiently. Scene cuts repeat the source frame. Low confidence, occlusion, deadline misses, thermal pressure, seek, or display changes bypass synthesis and return to MPV smoothing or source passthrough. Model warm-up must be asynchronous and never block playback startup.

On Android, NNAPI is deprecated in Android 15 and is not used as the NPU plan. LiteRT's documented accelerator interfaces are vendor-specific; where a device has no usable NPU delegate, the engine selects GPU/MPV or passthrough. This is provider resolution at runtime, not a platform-name claim.

Android LiteRT AARs and the C++ SDK are pinned to 2.3.0 by SHA-256 in `android/app/build.gradle.kts`. Run `scripts/motion/export_android_litert_models.py` outside the app build with the pinned ANVIL source and optional calibration inputs; point `PLEZY_LITERT_MODEL_ROOT` at its output directory to stage the checked manifest and `.tflite` files. Generic NPU records declare JIT execution. Google Tensor uses the target-specific AOT records described below; the Kotlin runtime resolver does not pass a JIT pack to Tensor devices. The app's LiteRT wrapper accepts fully NPU- or GPU-accelerated graphs only, and reports the provider family rather than inferring a vendor from the device name. This current bridge uses host-memory tensors, so it copies into the runtime and does not yet provide the LiteRT zero-copy AHardwareBuffer path.

## Enhancement modes

The planned session and provider scheduler will handle single-frame enhancement:

- **Restore:** deblocking and debanding for low-bitrate transcodes.
- **Upscale:** neural super-resolution remains planned. The existing MPV ArtCNN/NVScaler presets remain available on GPU MPV outputs, and Android ExoPlayer now has a separate opt-in Lanczos GL resampling preset for spatial enlargement. Lanczos is a scaler, not a neural model.
- **Order:** Restore → Upscale → Interpolate. Interpolation runs on cleaned frames; subtitles, OSD, and UI remain after video processing.
- **ExoPlayer:** Media3 GL effects provide single-frame spatial resampling. Neural Restore/Upscale needs a model-backed effect path; MPV owns timestamped interpolation until ExoPlayer receives a scheduler that can emit intermediate frames.

HDR10 is introduced only after the processing path preserves its transfer function and color metadata. Dolby Vision stays on the existing route until the filter is proven not to discard or corrupt its RPU/enhancement-layer behavior. The system falls back for Live TV and interlaced content unless a route implements their timing and field semantics.

## Model delivery and device qualification

`NeuralModelPackService` pins all ANVIL packs by revision, byte count and SHA-256. Desktop Performance uses the bundled 3.43 MB static 540p ANVIL-S graph (`6b599d7b13c848ce7608d5e6fa1de8ec0adea8477d29a57be69d71daf808ce84`); the app verifies it and copies it to private storage when Neural is selected. `scripts/motion/export_anvil_performance_model.py` recreates that graph from source commit `f701fd9b01b9fbb20822637b5d82cac626079e5f` and checkpoint revision `fa97e30f6aabe897bd4f6f82d971ad607f5d61fa` using PyTorch 2.9.1 and ONNX 1.17.0. Balanced downloads the upstream 3.44 MB 1080p ANVIL-S graph (`65e871aed25b331e3a3747cf9019942121a94af71997476f5804a24b768cd0d8`); Quality downloads the 10.68 MB 1080p ANVIL-M graph (`261f95a17c865b45e4d7e2be3439d91b47315bef96e32d46f3cfc785941774fd`). All downloaded packs install atomically after verification. The upstream model card marks the models MIT; the app includes its license.

The Android LiteRT route uses the same ANVIL checkpoints and exports fixed-shape NHWC `.tflite` variants: float32 for GPU and W8A8 for generic JIT-capable NPUs. The checked-in default pack in `assets/motion_models/litert` contains four float32 GPU variants (ANVIL-S/M at 720p/1080p; 28.35 MB total) and four W8A8 NPU candidates (7.57 MB total). Gradle verifies and packages all eight manifest-listed models by default; `PLEZY_LITERT_MODEL_ROOT` overrides the directory for calibrated or target-specific variants. The standalone exporter verifies the source checkout and upstream checkpoint size/hash, records every model's shape, precision, byte count, SHA-256, LiteRT-Torch version, and PyTorch version, then writes the manifest consumed by Gradle and Kotlin. The checked-in W8A8 comparison reports 40.74–43.76 dB aggregate PSNR against float32 outputs on calibration/validation pairs from one source clip. This is fidelity-to-float evidence, not ground-truth quality or device execution; see the [quantization evidence](evidence/android-litert-w8a8-validation-2026-10-28.md). No vendor-specific AOT models are included in the default pack. Export updated packs outside the app build. Omit calibration for the float GPU variants; add `--calibration-root` only when representative samples are available for W8A8 NPU JIT artifacts:

```sh
python3 scripts/motion/export_android_litert_models.py \
  --anvil-source /path/to/anvil-at-f701fd9 \
  --work-dir /path/to/task-scratch/anvil-checkpoints \
```

The generator produces two model contexts for each mapped SoC. V68/V69 devices use 720p; V73/V75/V79/V81 devices use 1080p. The target table includes SM7325, SM8350/SM8350P, SM7450, SM7475, SM8450/SM8475, SM8550, SM8650, SM8750, and SM8850. The ANVIL demo reports device measurements for SM7475, SM8550, and SM8650; the remaining mappings use Qualcomm's documented SoC IDs and HTP architectures and are implemented through the same fixed-shape pipeline. App builds supply both `QAIRT_SDK_ROOT` and `PLEZY_ANVIL_CONTEXT_ROOT`; Gradle checks the complete context set before staging it. The mpv filter accepts both 1280×720 and 1920×1080 planar YUV420 inputs and rejects other shapes before inference.

The device report is keyed by SoC/GPU, OS and driver build, provider, model-pack revision, decoder/output path, resolution, source cadence, and display cadence. Initial calibration exercises the same frame interop and provider session used during playback. Changes to the OS, driver, model, or decode path invalidate affected results. Performance/Balanced/Quality map to installed models and measured scales; the UI displays the provider that ran, p95 processing time, synthesis ratio, deadline misses, dropped frames, and fallback reason.

The target scheduler uses two source-frame pairs of queue depth. Flow inference for pair *n+1* can overlap the GPU warps for pair *n*. It tracks p95 latency and applies hysteresis: reduce model/scale, synthesize fewer timestamps, use MPV smoothing, then pass through. It steps down after repeated deadline misses and steps back up only after sustained headroom. Seek, stream discontinuity, display change, and track change flush the queue and resume from fresh source frames. The current desktop filter implements an initial safety governor: after three misses within two seconds it bypasses neural inference for ten seconds, then permits one recovery probe. Its asynchronous worker handles one inference job at a time; cross-pair overlap, cadence-exact output, and adaptive model-scale changes remain to be implemented.

The quality suite will cover pans, fast motion, cuts, animation, grain, subtitles, and logos. Quality reporting will include PSNR/SSIM/LPIPS against held-out real frames and a temporal-flicker metric. Runtime reports should separately show inference provider, actual NPU/GPU placement where available, copy/interop time, p50/p95 stage duration, A/V sync, drops, misses, and thermal state.
